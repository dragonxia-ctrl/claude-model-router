# v4 → v5: shorter Kimi residency with independent exit clocks

**Version report · 2026-11-26.** This document records why Kimi stayed sticky after v4, the public and local evidence behind the v5 exit rules, and what the change does and does not establish. Local numbers come from the live router log; the aggregates are in [`data/v4-v5.json`](data/v4-v5.json), regenerated by [`replay-v5.mjs`](replay-v5.mjs). Public numbers are cited with their source and version, because model aliases and harnesses differ from this installation's configured models.

---

## Abstract

v3 (1.3.0) removed the auxiliary-channel lock, and v4 (1.4.0) changed only update operations — neither shortened a Kimi stretch that was already running. A task that escalated to Kimi could still stay there for the rest of the turn. The only mid-turn exit counted **new tool calls** (24), and in the live log 33 of 38 consecutive Kimi runs never reached that count; the longest run spent 51 requests and 27.7 minutes on Kimi. After three failed probes, recovery also stopped permanently. v5 leaves escalation evidence, the default provider, explicit selection, the hard video capability, the clean-window thresholds, the 2-request probe and the 4-request minimum residency unchanged. It only adds **independent exit clocks** — a review after 6 Kimi requests or 5 elapsed minutes, in addition to 12 new tool calls — caps backoff at 16 requests, retries a clean checkpoint after an exhausted attempt cycle, and adds an authenticated state/manual-exit interface. Replaying the recorded requests, the share of sticky runs with at least one checkpoint opportunity rises from 5/38 to 28/38 and the number of opportunities from 6 to 68. This is a replay of *when a review could have opened*, not a measured de-escalation rate: the clean-window gate and the provider's response are not replayed, and all 10 probes recorded in the window returned HTTP 400.

---

## 1. Goal and constraints

The goal was narrow: **reduce the wall-clock and request length of a continuous Kimi stretch**, without changing what escalates to Kimi. The constraints were equally narrow:

- keep the default provider (DeepSeek), all escalation rules, and semantic triage unchanged;
- keep explicit model selection and the hard video capability authoritative;
- keep the probe length, clean-window thresholds, minimum residency, and relapse behaviour unchanged;
- ground every claim in a public source or a local measurement, and state what a replay cannot show.

## 2. Why Kimi still stayed sticky

### 2.1 The state machine had one mid-turn clock

Before v5, a probe could start only at a checkpoint, and a checkpoint was either a new human message or `windowToolCalls` (24) **new** tool calls since the last review, provided the Kimi residency had been served. The relevant condition was:

```js
const toolCallsSinceCheck = toolCallsNow - (previous.toolCallsAtCheck || 0);
const midTurn = previous.phase === 'kimi' && !newUser
  && toolCallsSinceCheck >= settings.windowToolCalls
  && residencyServed;
const checkpoint = newUser || midTurn;
```

Two kinds of long turn therefore had no exit at all:

- turns dominated by model output or long-running commands, which add few tool calls;
- turns whose tool calls are mostly reads or retries, so the *count* grows slowly relative to elapsed time.

### 2.2 Measured on the live log

The replay takes every interactive (`stream: true`) `route_decision` from 2026-11-25T04:09:01Z to 2026-11-26T08:38:27Z — 1 773 requests — groups consecutive `source: "sticky"` decisions into runs, and asks when the v4 and v5 clocks would have fired.

**Table 1.** Sticky runs and checkpoint opportunities in the recorded window.

| Measure | Value |
|---|---:|
| Interactive requests | 1 773 |
| Sticky requests | 548 |
| Sticky runs | 38 |
| Runs whose total tool-call delta was below 24 | **33 / 38** |
| Runs with at least one v4 checkpoint opportunity | 5 / 38 |
| Runs with at least one v5 checkpoint opportunity | **28 / 38** |
| v4 checkpoint opportunities | 6 |
| v5 checkpoint opportunities | **68** (63 request-clock, 3 tool-clock, 2 idle-clock) |
| Longest run | 51 requests / 27.7 minutes |
| Runs ≥ 6 requests (long enough for any review) | 30 |
| … of those, with a v4 opportunity | 5 |
| … of those, with a v5 opportunity | **28** |

The ten runs with no opportunity at all had 1–6 requests, all shorter than one v5 request window. In the other 28 runs the first v5 opportunity usually opened at request 6 (25 of 28 via the request clock). One run (`08e92d4698`, 2026-11-25 16:19) opened its first review at request 5 after 543 seconds, and the replay records that review as `idle_window`: the 5-minute clock fired before the request clock, which is exactly the case the tool-only clock could not see. Two further reviews in the window were `idle_window`, and only 3 of the 68 v5 opportunities came from the tool clock — 63 came from the new request clock. For the longest run, v4 offered 2 reviews; v5 offers 8, the first after 6 requests.

Replay method and its limits: the script does not simulate new-user checkpoints, the clean-window gate, residency, backoff, or upstream responses. A "v5 opportunity" means the request at which a review would have been evaluated, not that Kimi would have been left. The 68 figure is an upper bound on review openings, and the real effect on Kimi duration depends on how many of those windows pass the gate.

### 2.3 Recovery could also stop forever

With `maxAttempts: 3`, a task that failed three probes stayed on Kimi until a new task or explicit selection. In a long autonomous turn that is again an unbounded residency, and it is the same failure mode the release is trying to remove.

## 3. External evidence

### 3.1 DeepSeek vs Kimi on agentic and reasoning benchmarks

The DeepSeek-V3.2 report ([arXiv:2512.02556](https://arxiv.org/abs/2512.02556), Table 2) compares DeepSeek-V3.2-Thinking with Kimi-K2-Thinking on the same evaluation suite. The column order in that table places Kimi-K2-Thinking before DeepSeek-V3.2-Thinking; the values below are read from those two columns.

| Benchmark | Kimi-K2-Thinking | DeepSeek-V3.2-Thinking | Favours |
|---|---:|---:|---|
| Terminal Bench 2.0 (Acc) | 35.7 | **46.4** | DeepSeek |
| SWE Verified (Resolved) | 71.3 | **73.1** | DeepSeek |
| SWE Multilingual (Resolved) | 61.1 | **70.2** | DeepSeek |
| HLE (Pass@1) | 23.9 | **25.1** | DeepSeek |
| LiveCodeBench (Pass@1-COT) | 82.6 | **83.3** | DeepSeek |
| MMLU-Pro (EM) | 84.6 | **85.0** | DeepSeek |
| AIME 2025 (Pass@1) | **94.5** | 93.1 | Kimi |
| GPQA Diamond (Pass@1) | **84.5** | 82.4 | Kimi |

The report also states that DeepSeek-V3.2 "achieves comparable scores with substantially fewer output tokens" than K2-Thinking, and notes that its Terminal Bench 2.0 score of 46.4 was obtained with the **Claude Code framework** because its context management was incompatible with the benchmark's own Terminus harness. That is directly relevant here: this router is used by Claude Code.

What this supports — and what it does not:

- On the coding/agentic and research-style evaluations, keeping Kimi for the entire remainder of a turn is not supported by a demonstrated advantage; a review after a recovered window is defensible.
- On AIME and GPQA the public numbers still favour Kimi. That is why v5 does **not** touch escalation: math and hard-reasoning tasks still start on Kimi and still receive the full clean-window gate before leaving.
- The local aliases are `kimi-k3.1-pro` and `deepseek-flash`; the paper evaluates K2-Thinking and V3.2-Thinking. These are **proxies**, not the same model versions, harnesses, or serving stacks. No claim here is about the exact delta between the two aliases this router calls.

### 3.2 Routing literature: re-test the cheaper tier during the workload

- **RouteLLM** ([arXiv:2406.18665](https://arxiv.org/abs/2406.18665)) trains routers between a strong and a weak model and reports cost reductions of "over 2 times in certain cases — without compromising the quality of responses".
- **FrugalGPT** ([arXiv:2305.05176](https://arxiv.org/abs/2305.05176)) studies LLM cascades and reports matching the best individual LLM "with up to 98% cost reduction".
- **AutoMix** ([arXiv:2310.12963](https://arxiv.org/abs/2310.12963)) routes by self-verification of a smaller model's output and reports "reducing computational cost by over 50% for comparable performance".

The shared design idea is *repeated* routing decisions inside a workload, with the cheaper tier re-tested when evidence allows. v5 borrows only that principle: it does not import a learned router, a classifier threshold, or a cascade implementation, and it adds no dependency. The existing deterministic evidence rules still decide escalation.

### 3.3 Operational precedent: a failed trial is not a permanent state

The de-escalation machine is a half-open circuit breaker: bounded trials after failure, then either close (recover) or open again with backoff. Resilience4j and Polly implement the half-open state that way, and Envoy's outlier detection ejects and then cautiously reintroduces an upstream. What those systems do **not** do is treat an exhausted retry budget as permanent: a host that stays unhealthy is re-tested on a later interval. v5's `retryAfterExhaustedRequests` applies the same rule to probe attempts, using Kimi requests as the interval.

### 3.4 A directly relevant DeepSeek 400

OmniRoute issue [#20260](https://github.com/cheaper-inference/OmniRoute/issues/20260) documents DeepSeek `deepseek-flash` returning HTTP 400 `The "reasoning_content" in the thinking mode must be passed back to the API` on the Anthropic `/v1/messages` path, while the same history succeeds on `/v1/chat/completions`. The failing shape is an assistant turn that carries a tool call and no reasoning content; the project's fix injects a non-empty reasoning placeholder on the Anthropic path.

This router's provider switch strips `thinking` blocks before sending a Kimi history to DeepSeek, which produces exactly that tool-use-only assistant shape. All 10 probes in the measured window returned HTTP 400; their response bodies are not logged, so the specific error is unknown. Since v5, `sanitizeForProvider` inserts `{type: "thinking", thinking: " ", signature: ""}` when switching to DeepSeek, mirroring the OmniRoute workaround. This is a hypothesis-directed mitigation, **not a proven fix**: a minimal synthetic DeepSeek tool-use request returned 200 both with and without the placeholder, and the largest successful DeepSeek request in the log carried 234 031 input tokens including cache reads, so neither a trivial request shape nor a plain context limit explains the observed 400s by itself.

## 4. Local evidence

### 4.1 Replay, not re-execution

The replay reads only logged routing metadata: provider, source, stream flag, tool-call counts, timestamps, and probe request IDs joined to `request_complete` outcomes. Request bodies and responses are not stored, so it cannot evaluate the clean-window gate or whether a probe would have succeeded.

The `08e92d4698` runs are the clearest case: each ended below 24 new tool calls, so v4 never reviewed them, even though they ran for 5–10 minutes. The request clock opens a review after 6 requests regardless.

### 4.3 Probe outcomes in the window

Ten probe requests were recorded, all with `httpStatus: 400`. Their tool-call counts were 59–116, i.e. long, realistic histories rather than empty requests. This is important for interpretation: **v5 currently makes the probe cheaper to reach, not guaranteed to succeed.** If the 400s persist after deployment, Kimi residency will still be bounded by the review clocks and backoff, but fewer tasks will actually move to DeepSeek. The follow-up measurement is described in §7.

### 4.4 Engine-level experiments in the test suite

Five new tests exercise the exits directly, with no provider I/O:

- `a request-count checkpoint can start a probe without new tools or a new user message`;
- `an elapsed-time checkpoint can start a probe in a slow tool loop`;
- `an operator can schedule a manual de-escalation exit`;
- `exhausted normal attempts still have a bounded periodic retry exit`;
- `authenticated state and deescalate endpoints provide an operator exit`.

Each asserts an exit that v4 did not implement; the merged suite is 107 tests (102 on main before this change).

## 5. What v5 changes

| Area | v4 | v5 |
|---|---|---|
| Mid-turn review | 24 new tool calls | 12 new tool calls **or** 6 Kimi requests **or** 5 minutes, whichever first |
| Inspected recovery window | last 24 tool calls | last 12 tool calls |
| Backoff cap | 32 requests | 16 requests |
| After `maxAttempts` failed probes | Kimi until new task/explicit | Retry at a clean checkpoint after 16 Kimi requests (`0` disables) |
| Operator controls | — | `GET /v1/router/state`, `POST /v1/router/deescalate`, `claude-router state/deescalate` |
| Audit | outcome | + `deescalationCheckpoint`, `kimiRequests`, `requiredKimiRequests`, probe-outcome line |
| Provider switch to DeepSeek | strip incompatible thinking | also insert a reasoning placeholder (unproven mitigation, §3.4) |

Unchanged: default provider, escalation evidence and thresholds, semantic triage, explicit selection, hard video capability, `minKimiRequests: 4`, `probeRequests: 2`, `maxAttempts: 3`, the clean-window rules, and relapse-to-Kimi semantics.

### 5.1 Operator interface

```bash
claude-router state
claude-router deescalate --conversation <conversationKey>
claude-router deescalate --all
```

A manual request schedules a checkpoint and clears the failed-attempt cycle; the next main request still passes the clean-window and hard-capability gates. The state listing contains provider, phase, residency counters, attempts, probe successes, checkpoint baselines, and a `forced` flag — no task text, prompts, or message bodies.

## 6. Verification

- 107 offline tests pass (102 on main before this change). The new tests cover the request and time clocks, manual de-escalation, periodic retry after exhausted attempts, the control endpoints including authentication and 404 behaviour, the new log fields, and the sanitizer placeholder.
- The replay script reproduces `data/v4-v5.json` from `router.log`; the numbers in this report are generated from that file.
- Escalation is unchanged: the existing tests for the 20-mutation rule, explicit selection, hard video capability, and mid-turn tool review still pass without modification.
- The control endpoints require the local bearer token and return no task text.

## 7. Threats to validity

- **Opportunities are not switches.** 54 is the number of reviews that could have opened; the gate, residency, backoff, and provider responses are not simulated. The real de-escalation rate must be measured after deployment from `deescalation_probe_outcome` and `deescalationCheckpoint`.
- **The probe channel was failing.** 10/10 probes returned 400. The placeholder mitigation is based on one open-source issue and unproven for this installation; no claim is made that v5 shifts actual provider share until the 400s are explained.
- **Public benchmarks are proxies.** The paper's Kimi-K2-Thinking and DeepSeek-V3.2-Thinking are not necessarily the configured `kimi-k3.1-pro` and `deepseek-flash`; harnesses differ, and the paper's Terminal Bench score used Claude Code. The table is used to justify *re-testing*, not to assert a local quality delta.
- **No output-quality measurement.** This release measures routing decisions and probe outcomes, not answer quality. The safety argument is structural: every exit still requires a clean recent window, every failure relapses to Kimi within one request, and three failures return to backoff.
- **One installation and one window.** 1 773 requests over about 28.5 hours; the long-run distribution is installation-specific. The mechanism (a tool-count-only clock) is structural, the percentages are not.
- **Time clock and cache warm-up.** A 5-minute idle review can fire while a slow command is still running; that is intended, but it may evaluate a window whose tool results mostly predate the command.
- **In-memory state.** Router restarts clear residency; `state`/`deescalate` reflect only conversations routed since the last start.

## 8. Reproduction

```sh
node docs/versions/replay-v5.mjs --to 2026-11-26T08:38:27.294Z   # regenerate data/v4-v5.json
node docs/versions/replay-v5.mjs [path/to/router.log]   # replay a different log/window
npm test                                                # 107 offline tests
```

`--tools`, `--requests`, and `--idle-ms` override the three review clocks; the numbers in this report use the committed defaults (12 / 6 / 300 000).

The data file contains only request counts, timings, tool-call deltas, checkpoint kinds, first-ten-character conversation prefixes, and probe outcomes — no prompts, commands, or response bodies.

## 9. Follow-up measurement

After deploying 1.5.0, the next report should answer, from the log alone:

1. How many `route_decision` entries carry `deescalationCheckpoint` values, and of which kind (`tool_window`, `request_window`, `idle_window`, `manual`)?
2. How many `deescalation_probe_outcome` entries succeed? If 400s continue, capture the provider error `type`/`message` for one request — not the body — and test the placeholder hypothesis against a real failing history.
3. Did the maximum continuous sticky run length fall, and did any run exceed the 6-request / 5-minute review interval without a review? Those are the two direct tests of this release's goal.
